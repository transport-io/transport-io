## The whole thing

One file says what every event is and whether it can be dropped. Both ends import it.

```ts
// contract.ts
import { defineContract, type MapOf, reliable, unreliable } from 'transport-io'

export const contract = defineContract({
  chat: reliable<{ from: string; body: string }>(),
  cursor: unreliable<{ x: number; y: number }>(),
})

export interface AppMap extends MapOf<typeof contract> {}
```

<CardGrid>
<Card title="Server">
```ts
import { createServer } from 'transport-io'

const server = createServer<AppMap>({ contract })

server.onSession((peer) => {
  void peer.join('lobby')
  peer.on('chat', (m) => void server.to('lobby').emit('chat', m))
})

await server.listen(listener)
```
</Card>
<Card title="Client">
```ts
import { Client } from 'transport-io'

const client = new Client<AppMap>({ contract, connect })
await client.connect()

client.on('chat', (m) => render(m))

client.emit('chat', { from: 'me', body: 'hi' }) // arrives
client.emit('cursor', { x: 12, y: 40 })         // may not
```
</Card>
</CardGrid>

`chat` arrives. `cursor` may not. The contract is the only place that says so, and both
sides infer from it: a wrong event name or payload does not compile.

`AppMap` is passed once on each end, the way you would pass a router type to a typed client.
Nothing is registered globally and nothing is augmented.

## What that costs, compared

Socket.IO's own front page is eight lines of server and six of client, and neither is typed:
`socket.on('message', …)` gives you `any`, and nothing says whether a message can be dropped.

Typing it means declaring `ServerToClientEvents` and `ClientToServerEvents` by hand and
mirroring both as generics on `Server<…>` and `Socket<…>` at each end. Two interfaces, four
generic arguments, kept in step manually.

Here the contract is the source of both directions, `MapOf` derives the types, and each end
names it once. Reliability is part of it rather than a comment.

## Streaming responses

The server yields, the client consumes. Leaving the loop resets the QUIC stream. The
handler's `ctx.signal` fires and its `finally` runs.

<CardGrid>
<Card title="Client">
```ts
import { type Client, defineContract, type MapOf, streaming } from 'transport-io'

const gen = defineContract({
  ask: streaming<{ prompt: string }, string>(),
})
interface GenMap extends MapOf<typeof gen> {}

declare const client: Client<GenMap>
declare const prompt: string
declare const stop: boolean
declare function render(token: string): void

for await (const token of client.stream('ask', { prompt })) {
  render(token)
  if (stop) break
}
```
</Card>
<Card title="Server">
```ts
import type { Server } from 'transport-io'

declare const server: Server<GenMap>
declare function model(text: string): AsyncIterable<string>

server.handle('ask', async function* ({ prompt }) {
  for await (const token of model(prompt)) {
    yield token
  }
})
```
</Card>
</CardGrid>

Each `stream()` and each `call()` owns its own QUIC stream, so a stalled one does not block
the others.

## Before you start

These are properties of the library, not things it will grow out of.

- **Chrome and Firefox only.** Safari establishes a session and then never sends.
- **No fallback, deliberately.** A WebSocket would make the unreliable lane reliable, which
  is a lie about your data. An unsupported runtime gets `WT_NO_SUPPORT` and nothing else.
- **It needs raw UDP ingress to your process.** Many managed platforms do not provide it.
  Check yours before building on this.
- **`0.x`, so a minor bump may break you.** `0.2.0` renamed both lane values and changed the
  handshake; a `0.1.0` peer and a `0.2.0` peer refuse each other.
- **Every bidirectional stream leaks about 5.95 KB of server memory**, upstream in the QUIC
  binding rather than here. Streaming amortises it: a thousand tokens down one stream cost
  what one call does.

The credit window that bounds a streaming producer costs throughput: 27,470 elements per
